<h3 id="bank-mocks-h158">M3-Q20 (V2-D3.1)</h3>

<p id="sec-bank-mocks-p703" data-kind="prose"><strong>Scenario.</strong> A data agent has <code>export_csv</code> with no row limit. Its task
exports at most 100 rows. The team proposes logging exports.</p>

<p id="sec-bank-mocks-p704" data-kind="prose"><strong>Question.</strong> What is correct?</p>

<p id="sec-bank-mocks-p705" data-kind="prose"><strong>Options.</strong>
A) Keep the unlimited export and log it.
B) Limit the tool to 100 rows in the schema and scope it to the task.
Logging is observability, not the fix.
C) Remove all exports.
D) Add a second export tool.</p>

<p id="sec-bank-mocks-p706" data-kind="prose"><strong>Key.</strong> B. Decisive phrase: "no row limit... at most 100 rows." Why:
least privilege limits data visibility. The schema cap is the control.
Logs watch. Counterfactual: A wins never as the fix for an over-wide
tool.</p>

C) Remove the analytics reader used daily.
D) Remove the audit log.

<p id="sec-bank-mocks-p710" data-kind="prose"><strong>Answer.</strong> A, B</p>

<p id="sec-bank-mocks-p711" data-kind="prose"><strong>Key.</strong> A, B. The decisive phrase is &quot;identical... no marketing use.&quot; Overlap is the bloat signal. The database tool is not needed. The database tool is dangerous. You use C.</p>

<p id="sec-bank-mocks-p712" data-kind="prose">D blinds the team. There is no counterfactual.</p>


<h3 id="bank-mocks-h160">M3-Q22 (V2-D3.2)</h3>

<p id="sec-bank-mocks-p713" data-kind="prose"><strong>Scenario.</strong> A school bot shows student records. The design checks the
parent's login, then shows any student whose name the parent types.</p>

<p id="sec-bank-mocks-p714" data-kind="prose"><strong>Question.</strong> What is wrong?</p>

<p id="sec-bank-mocks-p715" data-kind="prose"><strong>Options.</strong>
A) Do nothing. The system checked the login.
B) This is authentication without authorization. The login proves the parent&#x27;s identity. Nothing checks the parent&#x27;s right to see the typed student.</p>

<p id="sec-bank-mocks-p716" data-kind="prose">Add the code check against the guardian roster.
C) The bot needs a bigger model.
D) Typing is too slow.</p>

<p id="sec-bank-mocks-p717" data-kind="prose"><strong>Key.</strong> B. The decisive phrase is &quot;checks the parent&#x27;s login, then shows any student whose name the parent types.&quot; This is why. Authentication without authorization is a locked front door with open rooms. The roster check is the missing authorization. A wins if the roster check exists.</p>


<h3 id="bank-mocks-h161">M3-Q23 (V2-D3.2)</h3>

<p id="sec-bank-mocks-p718" data-kind="prose"><strong>Scenario.</strong> A support agent needs to read the user's order history.
The design gives the agent the company's master API key.</p>

<p id="sec-bank-mocks-p719" data-kind="prose"><strong>Question.</strong> What is wrong?</p>

<p id="sec-bank-mocks-p720" data-kind="prose"><strong>Options.</strong>
A) Nothing. The agent needs access.
B) Confused deputy with ambient authority: the master key gives the
agent everyone&#x27;s orders. Use per-user delegated tokens with narrow
scopes instead.
C) The agent needs a bigger model.</p>

<p id="sec-bank-mocks-p721" data-kind="prose">D) Order history is not sensitive.</p>

<p id="sec-bank-mocks-p722" data-kind="prose"><strong>Key.</strong> B. Decisive phrase: "the company's master API key." Why: the
master key is ambient authority. Delegated per-user tokens carry the
real user's identity with least privilege. Counterfactual: A wins
never for a master key on user data.</p>

<p id="sec-bank-mocks-p725" data-kind="prose"><strong>Options.</strong>

B) Detect and classify: together they hold 3.9 of 4.4 seconds.
C) Store.
D) Add a filter stage.</p>

<p id="sec-bank-mocks-p726" data-kind="prose"><strong>Key.</strong> B. Decisive phrase: "detect 1.9 s, classify 2.0 s... SLA is
2.5 s." Why: the two stages hold 89% of the budget. The 1.9 s cut
must come from them. Counterfactual: A wins when download dominates.</p>
