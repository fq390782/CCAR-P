# 한국어 번역 스타일 가이드 (CCAR-F 재번역)

## 목표
한국어 모어 화자가 영어 원문을 보지 않고도 **한 번 읽고 이해**할 수 있어야 한다. 기존 번역의 문제는 영어 문장 구조를 그대로 따라간 **번역투**다. 단어를 옮기지 말고, 의미를 파악한 뒤 한국어로 **새로 쓴다**.

## 문장 (가장 중요)
1. 문장 단위로 대응시키지 않는다. 긴 영어 문장은 한국어에서 두 문장으로 나눠도 된다.
2. 영어식 표현을 푼다: 수동태 → 능동, 명사화("the addition of X") → 동사("X를 추가하는 것"), 긴 관계절 → 앞 문장으로 분리, 불필요한 대명사(It/This/They) → 주어 생략 또는 구체적 명사.
3. 주어·목적어를 한국어답게 생략하거나 바꿔 쓴다. "~에 의해", "~의 경우에", "~하는 것은 ~이다" 반복을 피한다.
4. 문제 본문은 "-다 / -는가?" 체, 해설은 "-다" 평서체. (기존 문체와 통일)
5. 보기는 짧은 구나 문장으로, 같은 문제 안에서 문체를 맞춘다. 원문 보기의 끝 마침표 유무는 따른다.
6. 원문의 문장 중간 줄바꿈(hard wrap)은 합친다. 단락 구분(빈 줄)은 유지. 똑같은 질문 문장이 두 번 반복되면 한 번으로 합쳐도 된다.

## 용어
- 기술 용어는 영어 원문 유지: hook, subagent, agent, system prompt, prompt, prompt caching, context, turn, loop, MCP, orchestration, escalation 등. 단 "tool"은 일반 명사일 때 "도구"로 쓰고, 식별자(get_customer 등)만 그대로 둔다. 조사는 자연스럽게(hook이 / subagent를).
- 일반 어휘는 한국어로. 한국 개발자가 쓰지 않는 **억지 번역어를 만들지 않는다**(예: ladder→"래더", counterfactual→"반사실 가정"). 그런 말은 뜻을 풀어 쓴다.
- 코드, 백틱(`...`), 파일명, 옵션(-p), 식별자, 숫자·단위·금액은 그대로.

## 충실성
- 의미를 더하거나 빼지 않는다. 정답·오답의 논리와 함정, "(A)" "(B)" 참조, `**D.**` 같은 마크다운 라벨은 보존한다.
- 원문이 틀렸거나 모호해 보여도 고치지 말고 그대로 옮긴다. 의심 사항은 출력의 `notes`에 적는다.

## 예시
- 원문: Headless CI use is what -p with JSON output and a schema is for: deterministic invocation, parseable results.
  나쁨(번역투): 헤드리스 CI 사용은 JSON 출력 및 스키마와 함께 쓰는 -p가 존재하는 이유이다.
  좋음: CI처럼 사람 없이 돌리는 환경에서는 `-p`에 JSON 출력과 스키마를 함께 쓴다. 호출 방식이 일정하고 결과를 그대로 파싱할 수 있기 때문이다.
- 원문: Move every subagent to the most capable model to cut retries
  나쁨: 재시도를 줄이기 위해 모든 subagent를 가장 유능한 모델로 옮긴다
  좋음: 재시도를 줄이려고 모든 subagent를 가장 성능이 높은 모델로 바꾼다

## 출력 형식
입력과 같은 길이·순서의 JSON 배열: `[{"id","question","choices":{"A":..},"explanation","notes"(선택)}]`. 보기 키는 입력과 동일.
